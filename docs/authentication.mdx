title: "Authentication & Premium Endpoint Gating"
description: "How user authentication and server-side session enforcement work in World Monitor — Clerk, cookies, and entitlement checks. No dashboard panel is plan-gated; a small, fixed set of RPC endpoints still are."
---

WorldMonitor uses [Clerk](https://clerk.com) for authentication. No dashboard panel is gated behind sign-in or a plan tier anymore — every panel renders for anonymous visitors. What remains plan-gated is a small, fixed set of RPC endpoints (`PREMIUM_RPC_PATHS`), enforced session-based via local JWT verification.

---

## Auth Stack

| Layer | Technology | Purpose |
|-------|-----------|---------|
| Auth provider | Clerk | Sign-in (email, social), session management, hosted UI |
| JWT verification | jose + Clerk JWKS | Server-side bearer token validation (no round-trip) |
| Convex integration | Clerk JWT template (`convex`) | Convex auth with `applicationID: "convex"` |
| Auth state | `auth-state.ts` | Reactive browser auth state, role caching |

### Key Files

| File | Purpose |
|------|---------|
| `convex/auth.config.ts` | Convex auth provider config — Clerk JWT issuer + applicationID |
| `src/services/clerk.ts` | Clerk instance init, `getClerkToken()` for Convex JWT template |
| `src/services/auth-state.ts` | Reactive auth state, role fetching, session hydration |
| `src/components/AuthHeaderWidget.ts` | Header sign-in button, Clerk UserButton |
| `server/auth-session.ts` | Server-side JWT validation with jose + cached JWKS |

## Premium Endpoint Gating

There is no more panel-level gating: `WEB_PREMIUM_PANELS`, `Panel.showLocked()`/`showGatedCta()`, the `PanelGateReason` type, and the locked-panel CSS have all been removed. Every panel in `src/config/panels.ts` renders for every user regardless of sign-in or plan — the `premium` field the type still permits on a `PanelConfig` is set on zero panels today.

What remains is a small, fixed **endpoint allowlist** — `PREMIUM_RPC_PATHS` — for the handful of generated-RPC paths that are still genuinely plan-gated (MCP access and a couple of API-tier/partner routes; see below). This is enforced at the RPC path level, not the panel level: a panel can be fully public while one specific mutation it (rarely) calls still requires a session.

Scheduled digest and alert-rule delivery (`/api/notification-channels`) is gated separately and isn't in `PREMIUM_RPC_PATHS` at all — it's a standalone Vercel function (not a generated-RPC path) that always requires a Clerk bearer, then checks `entitlements.features.tier < 1` itself and returns its own 403 ("Real-time alerts are available on the Pro plan.").

### How to gate a new RPC path

Two files must stay in sync:

#### 1. Path allowlist — `src/shared/premium-paths.ts`

```ts
export const PREMIUM_RPC_PATHS = new Set<string>([
  '/api/intelligence/v1/classify-event',
  '/api/forecast/v1/trigger-simulation',
  '/api/v2/shipping/route-intelligence',
  '/api/v2/shipping/webhooks',
  '/api/mcp-proxy',
  '/api/my-domain/v1/my-endpoint',  // <-- add here
]);
```

This single source of truth is imported by both the client (`src/services/premium-fetch.ts`, `src/services/runtime.ts`'s `WEB_PREMIUM_API_PATHS` alias) for Bearer-token injection, and the server gateway for enforcement.

#### 2. Server gateway — `server/gateway.ts`

The gateway imports `PREMIUM_RPC_PATHS`, validates the bearer token via local JWKS verification (jose), and checks `session.role === 'pro'` (falling back to a live Convex entitlement lookup for Dodo-subscribed users whose Clerk role claim hasn't caught up yet). Returns 403 if neither check passes.

### Currently gated endpoints

| Path | What it protects |
|------|-------------------|
| `/api/intelligence/v1/classify-event` | LLM-spend throttle — anonymous sessions fall back to keyword classification instead |
| `/api/forecast/v1/trigger-simulation` | On-demand simulation run outside the cached cron output (its read-side companion, `get-simulation-outcome`, is public) |
| `/api/v2/shipping/route-intelligence` | Partner-facing vendor compute (the public Route Explorer UI reuses this compute function directly rather than proxying the gated route) |
| `/api/v2/shipping/webhooks` | Partner webhook registration |
| `/api/mcp-proxy` | MCP access for browser-based Pro users |

No dashboard panel — including Stock Analysis, Backtesting, Daily Market Brief, WM Analyst, and every other panel formerly listed here — appears in this set.

### Desktop Behavior

Desktop users with a valid `WORLDMONITOR_API_KEY` in the Tauri keychain are treated as entitled on the endpoints above. The existing API key flow is unaffected — bearer tokens are a **second auth path**, not a replacement.

## Server-Side Session Enforcement

The Vercel API gateway accepts two forms of authentication for premium endpoints:

1. **Static API key** — `X-WorldMonitor-Key` header (existing flow, unchanged)
2. **Bearer token** — `Authorization: Bearer <clerk_jwt>` (for web users)

The gateway tries the API key first. If that fails on a premium endpoint, it falls back to bearer token validation using local JWKS verification via `server/auth-session.ts`. The JWT is verified against:
- **Issuer**: `CLERK_JWT_ISSUER_DOMAIN`
- **Audience**: `convex` (matches the Clerk JWT template)
- **Signature**: RSA256 via Clerk's published JWKS

Non-premium endpoints don't require any authentication from web origins.

## User Roles

User roles (`pro` / `free`) are stored as a `plan` claim in the Clerk JWT. The server extracts this from the verified token payload. Unknown or missing `plan` values default to `free` (fail closed — never pro).

On the client side, `getAuthState().user?.role` exposes the role. Both `isProUser()` and `hasPremiumAccess()` check this alongside legacy API key gates.
